# NTIP 0.1.0 release notes

> **Not tagged.** The Release workflow at this commit (`d7a1b00`) used the
> runner context where GitHub does not allow it, so the release was never
> published; 0.2.0 supersedes it. To see this state, check out `d7a1b00`
> instead of `v0.1.0` in the demo below.

**Simulation only, not for live dispatch.** A research prototype of an
advisory, human-in-the-loop triage platform for NG911 text and transcripts,
working on synthetic data only. Changes are listed in the
[changelog](../../CHANGELOG.md).

## Schema compatibility

- **1.x → 2.0.0 (breaking):** facts became source-aware, carrying evidence
  that points into a specific source event. 1.x documents do not validate
  against 2.x; the 1.x JSON Schema stays published in `backend/schemas/v1`.
- **2.0.0 → 2.4.0 (additive):** each minor version only adds:
  - 2.1.0: the `ReplayRun` record;
  - 2.2.0: model/rule disagreement conflicts and an optional `inference`
    section on incidents (absent means no model was used);
  - 2.3.0: the `eido_import` source type;
  - 2.4.0: the `close` review decision, the `closed` incident state and the
    `incident.closed` audit event.

  Documents written by any earlier 2.x version validate against 2.4.0.
  Consumers that match enums exhaustively must handle the new values.
- Every persisted record carries its `schema_version`, and records are never
  rewritten: older records are read as they were written.
- Database migrations are reversible (`--down`). Migration `0005` renumbers
  incident versions, and `0006` adds the `ntip_app` role, which deployments
  should connect as (see `backend/README.md`).

## Test and evaluation results

The release workflow re-runs the full test suite (against PostgreSQL 16),
the evaluation on the dev and regression splits, and the safety gate on the
tagged commit. It attaches the reports to the GitHub release, and each
report records that commit's SHA.

they describe these datasets only, not real-world accuracy):

## Known limitations

- **Not validated for real use.** All data is synthetic and labelled by the
  author. There have been no independent annotators and no practitioner
  review, and the figures above say nothing about real calls.
- **Rules miss things on unseen data:** B0 under-triaged 2 of 9 critical
  cases on the held-out test split. The default `rules_only` mode keeps a
  human reviewer on every assessment for this reason. The hybrid mode closes
  those two cases on this split, but B1 alone generalises poorly (DDL-014).
- **B2** (language model) is implemented but not evaluated, because that
  needs authorisation to call a paid external API. **B3** is not built.
- **Interop:** EIDO import maps notes only. Locations, persons and PIDF-LO
  are preserved but not mapped, and NENA-STA-024 conveyance is not
  implemented.
- **Access control:** tokens are static (no expiry, rotation or SSO), and
  incidents are not partitioned by tenant.
- **Language:** English plus some Spanish.
- **Location:** levels L3 (GIS reference) and L4 (standards mapping) need a
  licensed GIS dataset.
- **Not built yet:** stream replay with relative timing, the in-app
  evaluation report screen, and automated accessibility tests.
- **Licence:** the repository has no licence yet.

The [traceability matrix](../traceability-matrix.md) tracks every design
requirement and its status.

## Reproducible demo

Requires Docker with Compose.

```sh
git checkout v0.1.0
docker compose -f infra/docker/docker-compose.yml up --build
```

- Dashboard: <http://localhost:8080>. Enter a development token such as
  `dev-operator`.
- API docs: <http://localhost:8000/docs>.
- For the B1 model in hybrid mode, prefix the command with
  `NTIP_MODEL=b1-tfidf-logreg NTIP_INFERENCE_MODE=hybrid_review`.

To reproduce the evaluation (see `backend/README.md` for setup):

```sh
cd backend
uv sync --locked --extra dev --extra ml
uv run python -m ntip.interop.eido.fetch
uv run python -m ntip.evaluation --split dev --split regression
uv run python -m ntip.evaluation --split regression --gate
```
